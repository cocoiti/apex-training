# SPEC

このディレクトリはプロダクト全体の今の仕様を、領域ごとのファイルで持つ。

## 運用ルール

- SPEC は「今のプロダクトがどう振る舞うか」を書く。今後の計画や TODO は書かない。
- Issue は SPEC への変更・追加の依頼。PR で SPEC と実装・テストを一緒に更新する。
- 「なぜそうしたか」は SPEC ではなく ADR（`docs/adr/`）に書く。

## 書式（全領域で共通）

```
# <領域名>
## 概要
## 用語（必要なら）
## 振る舞い（機能ごとの小見出し）
## 受け入れ条件
```

受け入れ条件は「- **<ID>**: <条件> のとき <期待結果>」の形で、外から観測できる入力と期待結果だけを書く。
実装の内部（クラス名など）は書かない。

### 受け入れ条件の ID

- 新しく足す受け入れ条件の ID は `<接頭辞>-<Issue 番号>-<その Issue の中の番号>` にする。
  その Issue の中の番号は 1 から順に振る（例: Issue #81 で足す画面の条件は `UI-81-1`、`UI-81-2`。同じ Issue で構成の条件も足すなら `ARC-81-1`）。
  Issue 番号が違えば ID は重ならないので、並行して進める PR 同士で ID を振り直さなくてよい。
- 前からある `<接頭辞>-<番号>` の形の ID（`UI-43` など）はそのまま使い、新しい形に付け替えない。
- 既にある受け入れ条件の中身を変えるときは、その ID をそのまま使う（形が古くても新しくても）。
- 消した受け入れ条件の ID は欠番にして、どちらの形でも再利用しない。
- `UI-81` と `UI-81-1` は別の ID として扱う（一方を書いたテストや表の行が、もう一方を確かめたことにはならない）。
画面の文言（「開始」など）を日本語で書いた受け入れ条件は、言語を指定していなければ表示の言語が日本語のとき（[screens.md](screens.md)「表示の言語」）の条件とする。
