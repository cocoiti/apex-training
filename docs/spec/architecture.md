# 構成と拡張性

## 概要

リコイルの練習に加えて、追いエイム・フリックなどのエイムの練習と、将来のキャラコン（移動テクニック）練習を作り直しなしで足せるよう、
固定タイムステップのシミュレーション、アクションベースの入力、モードのプラグイン化、入力の記録と再生、
動く的・出てくる的と照準の当たりの判定を持つ。キャラコン自体は MVP の範囲外（[docs/roadmap.md](../roadmap.md)）。

## 用語

| 用語 | 意味 |
|------|------|
| シミュレーション | 照準・射撃・リコイル・練習の的の動き（将来は移動）の計算。`src/sim/` |
| 固定ステップ | シミュレーションを進める一定の時間間隔。既定 1/120 秒で、定数で変えられる |
| 補間の係数 | 最後のステップから次のステップまでのどこを描画しているかを表す 0 以上 1 未満の値 |
| ヨー・ピッチ | 照準の水平・垂直の角度（度）。ヨーは右が正、ピッチは上が正 |
| 箱 | 軸に平行な直方体。マップの壁と的を表す |
| 練習の的 | モードが練習ごとに置く的。マップの箱とは別に、位置が時間で変わる・出現して消える、を持てる（下の「練習の的」） |
| 照準のレイ | 目の位置から照準の向き（利用者の照準 + リコイルのオフセット）へ伸ばした半直線 |

## 振る舞い

### 固定ステップと描画の分離

- シミュレーションは固定ステップで進め、描画は画面の更新に合わせて別に行う。描画はシミュレーションの結果を補間して表示する。
- ループは蓄積方式で動く。描画のたびに前回からの経過時間を蓄え、蓄えた時間が固定ステップ以上ある間はステップを 1 つ進めて
  その分を差し引く。残った時間 ÷ 固定ステップを補間の係数（0 以上 1 未満）として描画に渡す。
- 1 回の描画で進める経過時間には上限（0.25 秒）があり、タブの切替などで長く止まったあとも、ステップをまとめて大量に進めない。
- 経過時間は差し替えられる時間の元から得るので、テストでは任意の描画間隔を与えてループを進められる。
- 同じ入力なら、表示のフレームレートが違ってもシミュレーションの結果は同じになる。

### シミュレーションの独立

- `src/sim/` は Three.js と DOM に依存しない。ブラウザなしでテストから実行できる。
- 描画（`src/render/`）はシミュレーションの状態を読むだけで、状態を書き換えない。シミュレーションは描画を参照しない。
- 描画はカメラをプレイヤーの目の位置に置き、照準の向き（利用者の照準 + リコイルのオフセット）にヨー・ピッチをそのまま合わせる。
  ヨーが正ならカメラは右を、ピッチが正なら上を向く。
- 描画は、出現している練習の的を、直前のステップと最後のステップの的の位置を補間の係数で補間した位置に表示する。
  出現していない練習の的は表示しない。
- 描画には、シーンに表示物を足し引きできる層がある。弾痕・ゴーストなどはモードがこの層に足し、層を空にすると表示から消える。
  層への追加・削除はシミュレーションの状態を変えない。
- 照準と弾道は 3D のベクトル（ヨー・ピッチの角度 → 方向ベクトル → 的とのレイの交差）で計算する。
- 座標は右手系で、単位はメートル。Y が上で、ヨー 0 度・ピッチ 0 度の向きは -Z（奥）。ヨーが正なら右（+X）、ピッチが正なら上（+Y）を向く。
- ピッチは -89 度〜+89 度に収める。ヨーは -180 度より大きく +180 度以下に正規化する。
- リコイルによる照準のズレは、カメラの向きに加える独立したオフセット（ヨー・ピッチ、度）として持つ。
  照準の向きは「利用者の照準 + リコイルのオフセット」で、利用者の入力はオフセットを書き換えない。

### 入力の消費

- 入力は発生時刻（練習の開始からの秒）付きでキューに積む。
- 各ステップは開始時刻以上・終了時刻未満の入力を、時刻の順（同じ時刻なら積んだ順）に消費する。
- ステップの開始より前の時刻の入力がまだキューに残っていたら、そのステップで消費する（捨てない）。
- `look` はヨー・ピッチの変化（度）で、そのステップで消費した分を足して照準に加える。
- `fire`・`ads` は押した・離したの状態で、そのステップで最後に消費した状態がステップの終わりの状態になる。
- テストでは、時刻付きのアクションの列をそのまま流す入力の元を使い、マウスやパッドなしでシミュレーションを動かせる。

### 種付きの乱数

- シミュレーションの乱数はすべて種付きの乱数から取る。種が同じなら同じ列、違えば違う列になる。
- 練習の種は練習を始めるたびに 1 つ決める。ふだんは練習ごとに予測できない値（0 以上 2³² 未満の整数）を選ぶので、
  同じ設定で練習しても的の位置・追いエイムの切り返し・武器のランダムなブレは練習ごとに変わる。
- テストからは、ページの URL で練習の種を決めた値に固定できる（下の「テストのための乱数の種の固定」）。
- ブラウザを使わないテストで練習やシミュレーションの乱数を作るときは、テストのコードに書いた決まった種から作る。
  種の違いで結果が変わることを確かめるテストも、比べる種をテストのコードに書いた値にする。
  練習の種を選ぶ処理そのもの（選ぶたびに値が変わること）を確かめるテストだけは、選んだ種を使ってよい。

### 練習の的

- モードは練習の準備とステップごとの処理で、マップの箱とは別に練習の的を置ける。練習の的は練習ごとに作り直し、ほかの練習に残らない。
- 練習の的は、識別子と、軸に平行な箱の大きさ（幅・高さ・奥行き、メートル）と、中心の位置の決め方を持つ。
  - 中心の位置は、練習の開始からの時刻（固定ステップの時刻、秒）から位置（メートル）を返す動きの関数で決める。
    位置の変わらない的は、時刻によらず同じ位置を返す。
  - 各ステップでは、そのステップの終わりの時刻で中心の位置を求める。位置は固定ステップの時刻だけで決まり、描画の間隔や実際の時計の時刻によらない。
- 練習の的は、出現の時刻と消える時刻を持てる。出現の時刻のステップから消える時刻のステップの前まで出現していて、
  それ以外のステップでは出現していない（照準の当たりにも弾の当たりにも入らない）。消える時刻を持たない的は、モードが消すまで出現している。
  モードはステップごとの処理で、的を足したり消したりできる。
- 出現の位置・時刻や動き方を乱数で決めるときは、その練習の種付きの乱数（下の「種付きの乱数」）から取る。同じ種なら、同じ位置・時刻・動きになる。

### 照準と的の当たり

- 各ステップで、そのステップの入力と射撃を適用したあとの照準のレイについて、出現している練習の的のそれぞれに「乗っている」かを求める。
  照準のレイが的の箱に当たり、その当たりがマップの箱と練習の的のなかで目の位置からいちばん近いとき、その的に「乗っている」。
  それ以外（外している、手前に壁がある、出現していない）は「乗っていない」。
- 撃った弾（[weapons.md](weapons.md) の当たり判定）は、マップの箱に加えて出現している練習の的とも当たりを求め、目の位置からいちばん近いものに当たる。
  練習の的に当たった弾は、当たった的の識別子を弾の記録に持つ（命中）。練習の的に当たった弾の弾痕は表示しない。
- 「乗っている」と弾の命中は、モードの採点（[scoring.md](scoring.md)「モードごとの採点」）が使う。

### 武器を使わない練習

- 武器を使わないモード（[modes.md](modes.md)「モードの登録」）の練習では、リコイルをかけない。照準のリコイルのオフセットは練習のあいだ
  ヨー 0 度・ピッチ 0 度のままで、照準の向きは利用者の照準と同じになる。
- 武器を使わない練習では、`fire` の押し始めのステップごとに 1 発を撃ったものとして、そのステップの照準のレイで弾の当たりを求める。
  押し続けても 2 発目は出ない。残弾はなく、弾は尽きない。

### 決まった結果

- シミュレーションの結果（照準、発射、弾痕、練習の的の位置と出現、照準と的の当たり、採点）は、武器のデータとマップのほかは入力の記録（時刻付きのアクションの列と乱数の種）だけで決まる
  （[input.md](input.md) の入力の記録と再生）。描画の間隔、実際の時計の時刻、デバイスには左右されない。
- 入力の記録を流す入力の元と、記録の種で作った乱数を与えれば、ブラウザなしで武器の発射から採点までのシミュレーションを実行できる。

### モードとマップの追加

- 練習モードは共通の型（`id`、`name`、`category`（recoil / aim / movement / combined）、武器を使うか、準備、ステップごとの処理、結果、
  採点、片付け）で作る。`aim` はエイムの練習（追いエイム・フリックなど）の種類。
  モードは任意で練習の選択肢（追いエイムの速さ、フリックの出る範囲と的の大きさなど、[modes.md](modes.md)「モードの登録」）を 1 つ以上持て、準備とステップごとの処理は選んだ値を受け取る。
- 練習の場所（マップ）は箱の組み合わせを `src/data/maps/` の JSON で定義する。
- プレイヤーは状態（MVP では「立ち止まって撃つ」だけ）を持ち、状態を足せる形にする。

### マップの形式

マップの JSON は次の項目を持つ。

| 項目 | 型 | 意味 |
|------|----|------|
| `id` | 文字列 | マップの識別子 |
| `name` | 文字列 | 表示名 |
| `spawn.position` | 数 3 つの配列 | プレイヤーの目の位置（x, y, z、メートル） |
| `spawn.yaw`・`spawn.pitch` | 数 | 開始時の照準（度） |
| `boxes` | 配列 | 箱の一覧 |
| `boxes[].id` | 文字列 | マップの中で一意な箱の識別子 |
| `boxes[].kind` | `"wall"` または `"target"` | 壁か的か |
| `boxes[].center` | 数 3 つの配列 | 箱の中心（メートル） |
| `boxes[].size` | 数 3 つの配列 | 箱の幅・高さ・奥行き（メートル、0 より大きい） |

- シミュレーションはマップの JSON の中身を受け取って World を作る。ファイルの取得はシミュレーションの外で行い、
  取得のパスはビルド時のベースパス基準にする。
- 必須の項目がない、型が違う、`kind` が `wall`・`target` 以外、`size` が 0 以下、`id` が重複している、のどれかに当たるマップは
  読み込みの誤りになり、どの項目が誤りかを返す。World は作られない。
- 1 つ目のマップ（`range`）は、プレイヤーの正面 10 メートルに壁が 1 枚あり、その手前に的が 1 つある。開始時の照準は的の中心を向く。

### フォルダ構成

```
src/
  core/      固定ステップのループ、時間、種付きの乱数、イベント
  input/     アクション定義、キーボード・マウス、パッド、割り当て、記録と再生
  sim/       World、Player（状態）、武器・リコイル、練習の的、当たり判定
  modes/     練習モード（recoil/, aim/, movement/, combined/）
  render/    Three.js のシーン・カメラ・弾痕・練習の的・ガイド
  ui/        メニュー・設定・リザルト（HTML/CSS）
  data/      weapons/, maps/
```

### 開発の手順

- セットアップ・開発サーバー・テスト・ビルドのコマンドはリポジトリの `CLAUDE.md`（技術スタック）に書いてある。
- ビルドの結果は、サブパス `/apex-training/` に置いて配信したときにすべてのファイルを読み込める。
- 全部のテスト（ブラウザを使うテストを含む）・lint・ビルド・配布物の検査は、下の「継続的インテグレーション（CI）」で流す。
  CI があることと、GitHub Actions の今の状態（有効で、GitHub がホストする標準の Linux の runner だけを使う）は `CLAUDE.md` に書いてある。

### 継続的インテグレーション（CI）

- リポジトリの GitHub Actions に CI のワークフローが 1 つある。PR を作ったとき・PR のブランチに push したとき（PR の更新）と、
  `main` に push したときに走る。
- CI は GitHub がホストする `ubuntu-latest` の runner の 1 つのジョブで動き、次を順に実行する。
  1. 依存の導入（`npm ci`）。Node.js は `CLAUDE.md` に書いた版を使い、npm のキャッシュを使う。
  2. lint・型の確認（`npm run lint`）
  3. ブラウザを使わないテスト（`npm run test:unit`）
  4. ブラウザを使うテストが探す場所（Playwright が置く Chromium のキャッシュ）への Chromium の導入。導入した Chromium はキャッシュして次の実行で使う。
  5. ブラウザを使うテスト（`npm run test:browser`）。runner の CPU が少ないので、同時に流すファイルの数は 2 にする（`APEX_BROWSER_WORKERS=2`）。
  6. ビルド（`npm run build`）
  7. サブパスでの配信の確認（`npm run check:subpath`）と、配布物が素材の一覧に載っていることの確認（`npm run check:assets`）
- どれかの段が失敗したら、それより後の段は実行せず、ジョブ（PR のチェック）は失敗になる。すべての段が成功したときだけ成功になる。
- CI では、Chromium が見つからないときにブラウザを使うテストを飛ばして成功にしない。Chromium が見つからなければ、ブラウザを使うテストの段より前か、その段で失敗になる。
- 同じブランチ（同じ PR）で新しい push があったら、そのブランチで走っている古い実行は取り消し、新しい実行だけを残す。
- CI は macOS・Windows の runner を使わない。GitHub Pages への公開（`gh-pages` ブランチへの push）は CI では行わず、今までどおり手動（`npm run deploy`）で行う。

### テストの実行

テストは、ブラウザ（Chromium）を使うテストと、ブラウザを使わないテストの 2 つの組に分かれる。

- `npm test` は両方の組を流す。ブラウザを使わない組を流し終えてから、ブラウザを使う組を流す（重い子のプロセスと画面のテストを重ねない）。ブラウザを使うテストだけを流すコマンド（`npm run test:browser`）と、
  それ以外だけを流すコマンド（`npm run test:unit`）もあり、`CLAUDE.md` のテストのコマンドに書いてある。
- テストが立てるサーバー（開発サーバー、ビルドの結果の配信、ブラウザの遠隔操作など）は、決まったポート番号で待ち受けない。
  ポート 0 で待ち受けて OS に空いているポートを選ばせ、実際に割り当てられた番号を読んで使う。
  人が開く用のポート（開発サーバーの 3100、プレビューの 3101、サブパスの確認の 3102）は固定のままにする。
- ブラウザを使わないテストは並列に流す。ブラウザを使うテストは、ファイル単位で既定で 2〜4 の範囲の決まった数（既定の並行数。値は `CLAUDE.md` に書く）を同時に流す。
  `npm test` と `npm run test:browser` のどちらでも同じ数で流す。
- 同時に流すブラウザを使うテストのファイルの数は、環境変数 `APEX_BROWSER_WORKERS` に 1 以上の整数を渡して変えられる。
  `APEX_BROWSER_WORKERS=1` なら今までどおり 1 ファイルずつ流す。1 以上の整数でない値を渡したときは、テストを流す前に
  その環境変数の名前を示して失敗する。変え方は `CLAUDE.md` のテストのコマンドに書いてある。
- ブラウザを使うテストのファイルを並行に流しても、ファイル同士でポート、Chromium のプロファイル、一時ディレクトリ、
  ビルドの結果を取り合わない。ファイルごとに別のものを使うか、全体で一度だけ作って読むだけにする。
- ブラウザを使うテストの待ちは、固定の時間の sleep ではなく、期待する状態（要素の表示、値の変化など）になるまで
  上限の時間つきで条件を確かめて待つ。上限を過ぎたら、何を待っていたかを示して失敗する。
- 同じマシンの別の作業ツリーで同時にテストを流しても、ポートの取り合いやブラウザのプロファイルの共有で互いに落とさない。
- ブラウザを使うテストは、Chromium をファイルごとに 1 回だけ起動し、テストごとにそのブラウザで新しいページを開く。
  テストのたびにブラウザを起動し直さない。

### テストのための描画の省略と時計の差し替え

- ページの URL のクエリに `render=off` を付けて開くと、3D の描画をしない。WebGL の文脈を作らず、描画の呼び出しもしない。
  それ以外（画面の遷移、HUD の文字、シミュレーション、採点、リザルト、設定と履歴の保存、パッドのメニュー操作）は
  付けないときと同じに振る舞い、同じ入力なら同じ結果になる。
- `render=off` を付けずに開いたときは、今までどおり描画する。利用者が開く URL には付かない。
- ページの URL のクエリに `clock=manual` を付けて開くと、ページの時計（固定ステップのループの経過時間、
  練習の終わりの「撃たない 2 秒」、短いリザルトの残り時間など、ページが時間で決めている振る舞いの時刻）は実時間で進まず、
  テストから指定した秒数だけ進む。実時間で待たなくても、指定した秒数がたったときと同じ振る舞いになる。
- 3D の描画が要らないブラウザのテストは `render=off` で開く。描画を確かめるテスト（画面の中心に的が見える、
  画面写しの色など）だけが描画する。仕様が時間を決めている所を確かめるテストは `clock=manual` で時計を進め、実時間で待たない。

### テストのための乱数の種の固定

- ページの URL のクエリに `seed=<数>`（0 以上 2³² 未満の 10 進の整数）を付けて開くと、そのページで始める練習の種は
  すべてその値になる（もう一度・連続練習で始め直した練習も同じ種）。同じ種・同じ入力なら、フリックの的の位置と出る時刻、
  追いエイムの的の動き、武器のランダムなブレが、開くたびに同じになる。入力の記録の種もその値になる。
- `seed` を付けないとき、または値が 0 以上 2³² 未満の整数でないとき（`abc`・`-1`・`1.5`・`4294967296` など）は無視し、
  ふだんどおり練習ごとに種を選ぶ。
- `seed` は `render=off`・`clock=manual` と同じく、テストのためのクエリで、組み合わせて付けられる。利用者が開く URL には付かず、
  画面（トップ、設定、プレイ、リザルト、履歴）に種を指定する操作も種の値の表示もない。画面の中のリンクや遷移で `seed` を付け足さない。
- ブラウザを使うテストは、練習を始めるページをすべて `seed` を付けて固定の種で開く。乱数で結果が変わるテスト（フリックの的の位置、
  追いエイムの切り返し、`randomness` が 0 でない武器のブレなど）だけでなく、練習を始めるテストはすべてそうする。
  使った種はテストのコード（テストの名前か本文、またはファイルに書いた定数）に書き、テストが失敗したときのメッセージにも
  使った種が出るので、同じ種で流し直せる。

### テストの網羅の分担

- ブラウザを使うテストで確かめる受け入れ条件と、それを確かめるテストのファイルの対応は、`tests/acceptance/README.md` の表に書く。
  1 つの受け入れ条件をブラウザで確かめるファイルは 1 つにし、同じ武器 × モードの組み合わせを複数のファイルで流さない。
- 表に載った受け入れ条件の ID は、表が示すファイルで、名前にその ID を含むテストが確かめる。
