Apex リコイル練習 Webアプリ — 仕様書（Claude Code向け）

このファイルをリポジトリ直下に置き、Claude Code に「SPEC.md を読んで MVP を実装して」と指示する想定。 調査日: 2026-11-25（Apex は Season 31「Cipher」、2026-11-03 開始）

## 1. 目的とコンセプト

ブラウザだけで Apex の武器のリコイル（反動）制御を練習できるツール。
マウスで撃ち、理想の補正軌道（ゴースト）と自分の補正のズレを可視化・採点する。

参考にする既存ツール:

- spray.training（CS:GO 向け、OSS）: 壁にスプレーし「ゴーストクロスヘア」を追う方式。Apex 版の直接の手本。 https://github.com/tobratland/spray.training
- reflextester.fun の Apex Recoil Trainer: R-301 / R-99 / フラットライン / ボルト対応、ダミーにスプレー、ダメージ・HS率を表示。
- Aiming.Pro（Apex 向けドリル・感度合わせあり）、Steam の Recoil Trainer（パターン再構築・ガイド表示）。

差別化案: 実感度（DPI・感度・FOV）を正確に再現、パターンを JSON で編集・共有できる、1発ごとのズレ分析。

## 2. 重要な前提・制約

- 公式のリコイル数値データは存在しない。 出回っているのはコミュニティが射撃訓練場で計測した画像、モバイル版の表示、データマイナーの映像など。 → 武器データはハードコードせず JSON で外部化し、後から差し替え・追加できる設計にする。
- シーズンごとに武器調整が入る（例: S30「Marked」でエネルギー武器の仕組みを全面改修、S31 で「アキンボ・ウィングマン」追加）。 → JSON に version（シーズン名）と source（計測元）フィールドを持たせる。
- 権利まわり: EA / Respawn の画像・ロゴ・武器モデル・効果音は使わない。武器名はテキストのみ。フッターに「非公式ファンツール、EA/Respawn とは無関係」と明記。
- マクロ・チート扱いになる機能は作らない。 ゲーム起動中に自動でマウスを動かす、パターンを外部に出力して自動補正させる、などは禁止。あくまで「ブラウザ内での練習」に限定。
- マウスとパッド（コントローラー）の両対応。 入力方式はアプリ内で切替可能、最後に操作したデバイスを自動検出。スマホ単体（タッチ）は非対応でよいが、パッドを接続していればタブレット等でも遊べるようにする（Gamepad API はモバイルブラウザでも動く）。
- パッドのエイムアシストは再現しない。 内部の値は非公開で、2026年もアンチチート更新に伴って挙動が変わっている（7月の更新後、Respawn 自身が長距離を中心にパッドの命中率が約2〜4%下がったと発表）。アプリでは「エイムアシストなしの素のリコイル制御を練習する」と明記する。
- チート用途への転用を防ぐ。 Cronus 系デバイスや RC フィルターの調整ツールに使える出力（補正値のエクスポート、外部デバイス連携）は作らない。

## 3. 技術スタック（推奨）

- Vite + TypeScript + Three.js（最初から 3D）
  - 将来キャラコン（移動練習）を入れるため、MVP の段階から一人称 3D カメラで作る。2D で作って後から 3D に移すと描画・座標系・入力をほぼ作り直すことになるため。
  - リコイル練習モードは「カメラ位置固定・壁と的だけの 3D シーン」として作れば、見た目も操作も 2D 版と同等の手間で済む。
  - 照準・弾道は最初から **3D ベクトル（ヨー/ピッチ角 → 方向ベクトル → レイキャスト）**で計算する。
  - UI（メニュー・設定・リザルト）は HTML/CSS で 3D キャンバスの上に重ねる。
- 当たり判定・物理: 当面は自前の簡易判定（箱・カプセル同士）。地形が複雑になった段階で Rapier（WASM 物理エンジン）を検討。移動の手触り自体は物理エンジン任せにせず自前の計算で作る（§9 参照）。
- 状態管理はシンプルに（素の TS か Zustand 程度）
- 永続化: localStorage（設定・自己ベスト）。try/catch で囲む
- テスト: Vitest（感度換算・採点ロジックのユニットテスト）
- デプロイ: GitHub Pages（サーバー不要の静的サイトなのでそのまま載る）
  - vite.config.ts の base を '/<リポジトリ名>/' にする（<ユーザー名>.github.io リポジトリなら '/'）
  - GitHub Actions で main に push → npm ci && npm run build → dist/ を Pages に公開するワークフローを .github/workflows/deploy.yml に用意
  - リポジトリ設定の Pages → Source を「GitHub Actions」にする
  - 武器・マップの JSON や音声は public/ に置くか import する。読み込みパスは import.meta.env.BASE_URL 基準にする（直書きの /data/... はサブパスで 404 になる）
  - 画面切替はハッシュ方式（#/settings など）にする。Pages はサーバー側のリダイレクトが使えず、通常のパスで直接開くと 404 になるため
  - 公開サイトは 1GB まで。3D モデルや音声は軽量に保つ

## 4. 入力まわり（ここが品質の肝）

### 4.1 Pointer Lock + 生入力

- キャンバスクリックで canvas.requestPointerLock({ unadjustedMovement: true })。
- unadjustedMovement: true で OS のマウス加速を無効化した生の移動量が取れる（Chrome 88+）。
- 非対応ブラウザでは Promise が返らない／reject される → 通常の requestPointerLock() にフォールバックし、「マウス加速が効いている可能性あり」と警告表示。
- pointerlockchange / pointerlockerror を監視。Esc でロック解除 → 一時停止画面。
- 移動量は mousemove の movementX/Y を累積して使う。高ポーリングレートのマウス向けに pointerrawupdate が使えれば優先。
- 全画面（Fullscreen API）ボタンも用意。

### 4.2 感度換算（Apex と同じ手触りにする）

- Apex は Source 系エンジンで yaw = 0.022°/count（CS2 と同じ）。
- 角度(°) = カウント × 感度 × 0.022
- cm/360 = 360 / (DPI × 感度 × 0.022) × 2.54
- ADS 時: 角度 = カウント × 感度 × ADS倍率 × 0.022（ADS倍率はユーザー入力。Apex の「ADS感度倍率」をスコープ別に入れられるとなお良い）
- 設定画面の入力項目: DPI / 感度 / ADS倍率 / FOV。cm/360 を表示。
- 画面への投影: 角度 → ピクセルは視野角から計算。
  - px = (tan(角度) / tan(水平FOV/2)) × (画面幅/2)
  - ⚠️ 要確認: Apex の FOV スライダーは 4:3 基準の値とされる（設定 110 ≒ 16:9 で約 120°）。換算式は実装時に再確認し、定数化しておく。

### 4.3 パッド入力（Gamepad API）

取得方法

- Gamepad API はイベントではなくポーリング式。gamepadconnected で検出し、毎フレーム navigator.getGamepads() をループ内で呼び直して最新状態を読む（参照を保持しても更新されない）。
- 接続直後は何かボタンを押すまで検出されないので、「パッドのボタンを押してください」と案内を出す。
- gamepad.mapping === "standard" なら標準配置:
  - axes[2], axes[3] = 右スティック X/Y（視点操作）、axes[0], axes[1] = 左スティック
  - buttons[7] = R2/RT（射撃、value 0〜1 のアナログ値）、buttons[6] = L2/LT（ADS）
- standard でない場合（一部のサードパーティ製など）はボタン割り当て画面を出す
- 同じパッドでも USB と Bluetooth で値が違うことがあるので、生の値を見られるキャリブレーション画面を用意（スティックドリフトの確認＋デッドゾーンの目安表示）。
- 振動: gamepad.vibrationActuator?.playEffect("dual-rumble", …) を射撃時に軽く（設定でOFF可）。非対応なら無視。

スティック → 視点回転（マウスとの根本的な違い）

- マウスは「移動量＝角度」だが、パッドは「傾き＝回転速度（°/秒）」。毎フレーム 角度 += 速度 × dt で積分する。
- dt は performance.now() の差分で計算し、フレームレートが違っても回転量が同じになるようにする。
- Apex の詳細視点設定（ALC: Advanced Look Controls）に寄せたパラメータを用意:

| パラメータ | 内容 | 初期値の例 |
|-----------|------|-----------|
| デッドゾーン | 中心付近の無効範囲（%） | 5〜15% |
| 外側しきい値 | 端の何%で最大入力扱いにするか | 1〜5% |
| レスポンスカーブ | 傾き→速度の曲線。0〜2 ≒ リニア、8 前後 ≒ クラシック | 指数で近似 |
| ヨー速度 / ピッチ速度 | 水平 / 垂直の最大回転速度（腰撃ち） | 300 / 260 程度 |
| ADS ヨー速度 / ADS ピッチ速度 | ADS 中の速度 | 腰撃ちの 25〜40% 程度 |
| 追加ヨー / 追加ピッチ・立ち上がり時間・遅延 | スティックを倒し切った時の加速 | 0（リコイル練習では基本不要、拡張扱い） |

- ⚠️ Apex 内部の正確な計算式は非公開。 上の名前と初期値はプロ設定の公開例に合わせた近似。**「ゲームと完全一致」ではなく「近い感覚で練習できる」**と UI に書く。式は src/input/padCurve.ts に分離し、後から調整しやすくする。
- 簡易モード（ALC OFF 相当）: 「視点感度 1〜6」「ADS 感度」「カーブ：クラシック / リニア」だけ選べるプリセットも用意。

パッド向けの練習ガイド

- マウス向けのゴースト（理想の軌道）に加えて、**「今スティックをどの方向にどれだけ倒すべきか」**をスティック型の円で表示するガイドを出す（理想の補正速度を、設定したカーブの逆関数で傾き量に変換）。
- リザルトで自分の右スティック入力の推移と理想の推移を重ねたグラフを表示（「序盤の引き下げが遅い」「後半で横に流れる」などが分かる）。
- R2 のアナログ値はしきい値（例 0.5）で射撃判定。

### 4.4 入力方式の共通化

InputSource インターフェースで抽象化し、マウスとパッドを差し替え可能に:

```ts
interface InputSource {
  update(dt: number): void;
  getAimDelta(): { yawDeg: number; pitchDeg: number }; // そのフレームの視点変化量（度）
  isFiring(): boolean;
  isADS(): boolean;
}
```

- リコイル・採点・描画は角度（度）だけを扱い、入力方式を意識しない。
- 設定・自己ベストは入力方式ごとに別管理（マウスとパッドの成績を混ぜない）。

## 5. リコイルモデル

### 5.1 武器データ（/src/data/weapons/*.json）

```json
{
  "id": "r301",
  "name": "R-301",
  "version": "S31-Cipher",
  "source": "community measurement (要差し替え)",
  "rpm": 816,
  "magSize": 28,
  "pattern": [
    { "dx": 0.00, "dy": 0.00 },
    { "dx": 0.05, "dy": 0.40 }
  ],
  "randomness": 0.05
}
```

- pattern[i] = i 発目で照準が跳ね上がる量（度）。右が +dx、上が +dy。
- randomness = 各発の ±ブレ（度）。0 で完全固定パターン。
- 発射間隔 = 60000 / rpm ms。フレームレートに依存しないよう performance.now() で時間を積算して発射判定する。
- MVP の武器（ジャンル別に代表）: R-301、R-99、フラットライン、ボルト、スピットファイア（LMG）。数値は仮データでよい（形状だけそれっぽく：例 R-301 は上→やや右→左に流れる）。後で計測データに差し替える。

### 5.2 弾の着弾位置

- 照準方向 = ユーザーのマウス累積角度 + リコイル累積角度
- 完璧に補正した場合、全弾が中心に集まる。
- 撃ち終わり（左クリック離す／マガジン切れ）でリコイル累積を一定時間で回復（簡易でOK）。

## 6. 練習モード

| モード | 内容 | 優先度 |
|--------|------|--------|
| パターン観察 | 補正なしで撃ち、壁に弾痕を残す。パターンの形を覚える | MVP |
| ゴースト追従 | 理想の補正軌道（パターンを上下左右反転したもの）を点で表示し、それに沿ってマウスを動かす | MVP |
| センター維持 | ゴーストなし。中心の的に弾をまとめる。採点あり | MVP |
| ダミー射撃 | 人型シルエット（自作の図形）に撃ち、ダメージ・HS率を表示 | 次 |
| 移動ターゲット | 左右にストレイフする的を追いながら補正 | 次 |
| パターン編集 | 弾痕をドラッグして独自パターンを作成 → JSON エクスポート/インポート | 次 |

## 7. 採点・分析

- 各弾について中心からの角度ズレを記録。
- 表示する指標:
  - 平均ズレ（度）、グルーピング半径（95%円）、命中率（的の半径内）
  - 前半 / 中盤 / 後半のズレ比較（どこで崩れるか）
  - 横ブレ vs 縦ブレの比率（「下げすぎ」「横補正不足」などコメント）
- リザルト画面: 弾痕の散布図 + 自分のマウス軌道 vs 理想軌道の重ね描き。
- 武器ごとの自己ベストを localStorage に保存。

## 8. 画面構成

- トップ: 武器選択（カテゴリ別）、モード選択、「開始」
- 設定: 入力方式（マウス / パッド / 自動）、FOV、クロスヘア色・形、ゴースト表示ON/OFF、音ON/OFF（効果音は自作 or Web Audio で合成）
  - マウス: DPI / 感度 / ADS倍率
  - パッド: 簡易プリセット or ALC 相当の詳細項目、振動ON/OFF、ボタン割り当て、キャリブレーション（スティックの生の値を表示）
- プレイ画面: 全画面キャンバス。HUD に残弾・武器名・経過時間
- リザルト: 指標 + 散布図 + 「もう一度」「武器変更」

## 9. 将来の拡張: キャラコン（移動テクニック）練習 — 今から設計に入れておくこと

キャラコン自体は MVP では実装しない。ただし後から追加しても作り直しにならない土台を最初から作る。

### 9.1 想定している将来の練習内容

- ストレイフ撃ち（左右に動きながらスプレー）、しゃがみ撃ち
- スライド、スライドジャンプ、バニーホップ
- 壁ジャンプ、よじ登り（マントル）ジャンプ
- スーパーグライド、タップストレイフ、ラーチ等の高度なテク
- 移動しながらのリコイル制御（キャラコン × リコイルの複合練習）
- ⚠️ 各テクの仕様（入力受付時間、速度、ゲーム側の修正・弱体化の有無）はシーズンで変わるため、実装時に最新情報を調べてから数値を決める。

### 9.2 土台として最初から作るもの

① 固定タイムステップのシミュレーションループ

- ゲームの計算（移動・射撃・リコイル）は一定間隔（例: 1/120秒）で進める。描画は requestAnimationFrame で別に回し、計算結果を補間して表示する（いわゆる「固定ステップ＋蓄積」方式）。
- 理由: 移動テクは「何フレーム以内に入力したか」で成否が決まるものが多く、モニターのリフレッシュレートで結果が変わってはいけない。スーパーグライドのように本家でもフレームレートの影響を受けるテクもあるため、計算レートは設定で変えられる定数にしておく。
- リコイルの発射判定（§5.1 の時間積算）もこのループに乗せる。

② 「アクション」ベースの入力

- 入力をキーやボタンではなくアクション名で扱う: move（2軸）, look（2軸）, fire, ads, jump, crouch, sprint, reload …
- §4.4 の InputSource をこれに拡張し、キーボード＋マウス／パッドの両方から同じアクションが出るようにする。キー割り当て変更（マウスホイールにジャンプを割り当てる等）もこの層で対応。
- 各入力に発生時刻（event.timeStamp / performance.now()）を付けてキューに積む。シミュレーションはステップごとに、その時間内の入力を消費する。→ 「ジャンプとしゃがみの間隔が何ms だったか」を正確に測れる。

③ プレイヤーの状態マシン

- Player は状態（地上 / 空中 / しゃがみ / スライド / よじ登り / 壁接触 …）を持ち、状態ごとに移動の計算を切り替える。MVP では「立ち止まって撃つ」状態だけ実装し、状態は後から追加できる形にする。
- カメラはプレイヤーの目の位置に付ける。リコイルの照準ズレはカメラの向きに加算する独立したオフセットとして持ち、移動とは混ぜない。

④ 移動パラメータのデータ化

- 武器と同じく、移動の数値（歩き/走り速度、加速・摩擦、空中制御、ジャンプ力、スライド関連）を /src/data/movement.json に外出しする。最初は仮の数値でよく、実機と見比べて調整する。
- 移動の計算は Source 系ゲームでおなじみの「地上加速・摩擦・空中加速」の考え方をベースに自前で書く（物理エンジンには任せない）。

⑤ 練習モードのプラグイン化

各練習モードを共通の型で作り、モードの追加 = ファイルを1つ足すだけ、にする:

```ts
interface TrainingMode {
  id: string;
  name: string;
  category: "recoil" | "movement" | "combined";
  setup(world: World): void;         // シーン・的・プレイヤー初期位置
  step(world: World, dt: number): void; // 固定ステップごとの処理
  getResult(): ModeResult;            // 採点結果
  dispose(): void;
}
```

- マップ（練習コース）は箱の組み合わせを JSON で定義（/src/data/maps/*.json）。壁ジャンプ用の壁、スライド用の坂などを後から足せるようにする。

⑥ 入力の記録とリプレイ

- 1回の練習の入力列（時刻付き）を保存しておけば、同じ計算を再実行してリプレイ・スロー再生・入力タイミングの表示ができる。そのためシミュレーションの結果が入力だけで決まるように作る（ランダム要素は種付きの乱数を使う）。
- 当面はリザルト画面のリコイル軌道表示に使い、キャラコン追加時に「入力タイミングのグラフ」に流用する。

### 9.3 フォルダ構成の目安

```
src/
  core/      ループ（固定ステップ）、時間、種付き乱数、イベント
  input/     アクション定義、キーボード・マウス、パッド、割り当て、記録/リプレイ
  sim/       World、Player（状態マシン）、移動計算、武器・リコイル、当たり判定
  modes/     練習モード（recoil/, movement/, combined/）
  render/    Three.js のシーン・カメラ・弾痕・ガイド表示
  ui/        メニュー・設定・リザルト（HTML/CSS）
  data/      weapons/, movement.json, maps/
```

sim/ は Three.js や DOM に依存させない（純粋な TypeScript）。テストしやすく、リプレイも確実になる。

## 10. 実装ステップ（Claude Code への分割指示用）

0. 土台（§9.2）: §9.3 のフォルダ構成、固定タイムステップのループ、アクションベースの入力、TrainingMode の型、sim/ と描画の分離
1. Vite + TS + Three.js のプロジェクト作成、一人称カメラの 3D シーン（壁と的）を全画面表示、Pointer Lock（unadjustedMovement とフォールバック）
2. 感度換算モジュール + ユニットテスト（cm/360 が既知の値と一致するか）
3. 武器 JSON ローダー + 発射ループ（時間積算方式）+ リコイル適用
4. 「パターン観察」「センター維持」モード + 弾痕描画
5. 「ゴースト追従」モード
6. 採点ロジック + リザルト画面 + localStorage 保存
7. 設定画面（マウス）
8. InputSource 抽象化 → パッド入力（Gamepad API ポーリング、デッドゾーン、レスポンスカーブ、速度の積分）＋ユニットテスト
9. パッド用の設定画面・キャリブレーション画面・スティックガイド・入力推移グラフ
10. 追加モード（ダミー、移動ターゲット、パターン編集）

入力の抽象化（手順8）は手順0で先に作っておくと手戻りが少ない。Claude Code には「最初から InputSource 経由で実装して」と伝える。 キャラコン（§9）は MVP の範囲外。ただし手順0の土台は省略しないこと。

## 11. 受け入れ基準（MVP）

- [ ] Chrome でポインターロック＋加速無効の生入力が動く（非対応時は警告）
- [ ] DPI 800 / 感度 1.5 で cm/360 ≈ 34.6 と表示される
- [ ] 60Hz と 144Hz のモニターで同じ RPM・同じ弾数で撃てる（フレームレート非依存）
- [ ] 5 武器でパターン観察・ゴースト追従・センター維持が遊べる
- [ ] 武器 JSON を追加するだけで新武器が選択肢に出る
- [ ] PS5（DualSense）と Xbox のパッドで、右スティックで照準、R2 で射撃、L2 で ADS ができる
- [ ] スティックを同じだけ倒したとき、60Hz と 144Hz で回転量が同じ
- [ ] デッドゾーン内のドリフトで照準が動かない
- [ ] マウスとパッドの自己ベストが別々に保存される
- [ ] 拡張性: 新しい練習モードを src/modes/ にファイルを1つ足すだけで追加できる
- [ ] 拡張性: sim/ が Three.js・DOM を import していない（テストで確認）
- [ ] 拡張性: 記録した入力列を再生すると、同じ弾痕・同じスコアが再現される
- [ ] EA/Respawn の素材を一切使っていない、非公式表記がある

## 12. 未解決・あとで決めること

- 正確なリコイルデータの入手方法（自分で射撃訓練場で計測して JSON 化するのが現実的。パターン編集機能がそのまま計測ツールにもなる）
- Apex の FOV 換算式の正確な定義
- アタッチメント（バレル等）による反動軽減の扱い（倍率係数で簡易対応が無難）
- パッドのレスポンスカーブ・速度の、Apex 実機との一致度（実機と見比べて定数を調整）
- エイムアシスト風の「的の近くで感度が落ちる」簡易オプションを付けるか（付けるなら初期値 OFF、「再現ではない」と明記）
