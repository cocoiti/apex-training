# L-STAR の跳ねは録画の画面の動きから求め、FOV の値の Hor+ 換算（ADS の倍率なし）で角度にする

## 状態

承認

## 背景

- Issue #17 で L-STAR の武器データを、自分で撮影した射撃訓練場の録画（FOV 104・アイアンサイトで ADS・射撃中の照準操作なし）からの計測値にする。
  撮影時のアタッチメントはすべて紫（レベル 3）だった（Issue #49 で訂正。[2026-11-25-measure-with-all-purple-attachments](2026-11-25-measure-with-all-purple-attachments.md)）。
- 壁の弾痕は重なって筋になり、1 発ずつは分けられない。
- ピクセルから角度への換算には FOV の値から視野角を求める式が要る。Apex の正確な換算式も、ADS で視野角がどれだけ狭まるかも公表されていない。
- アプリの描画（PR #22 で入る予定の `src/render/fov.ts`）は FOV の値を 4:3 での水平視野角とみなす Hor+ の近似を使い、ADS の拡大はしない。

## 決定

- 連続するフレームの画面の上部（照準器・マズルフラッシュ・固定の表示を除く範囲）の平行移動を位相相関で求めて足し合わせ、
  各発の跳ねが収まった時点の視点の位置を、その発の跳ねとする。i 発目の角度は 1〜(i-1) 発目の跳ねの合計（1 発目は 0）。
- ピクセルから角度への換算は、アプリと同じ Hor+ の式（縦 = 2·atan(tan(FOV/2)/(4/3))、水平 = 2·atan(tan(FOV/2)·A/(4/3))、
  中心から x px の点は atan(x/(幅/2)·tan(水平/2))）を、録画のゲーム画面 1280x800 で使う。相関を取った範囲の中心の点が
  画面の動きでどこに移ったかを式で角度にし、その差を視点の回転とする。ADS による視野角の狭まりは換算に入れない。
  記録の角度は「FOV 104 の腰だめの画面で同じ大きさに見える角度」になり、アプリを FOV 104 で描くと録画と同じ大きさに見える。
- 計測の記録（射撃ごとの各発の角度と画面の動きのピクセル、換算の条件、許容差）は数値だけを `docs/measurements/lstar.json` に置く。
  解析のスクリプトと動画・切り出したフレームはリポジトリの外に置く。換算が式どおりかはテストがピクセルから計算し直して確かめる。
- リコイルの正確なデータは、射撃訓練場を自分で録画し、この方法で計測して入手する。L-STAR 以外の武器も同じ方法で計測できる。
- これは**未確認の近似**である。Apex の FOV の換算式が違う、または ADS の倍率（腰だめと ADS の壁の大きさの比では約 1.45 倍）を
  角度に入れるべきと分かったときは、記録のピクセルから計算し直し、この ADR を置き換える。

## 却下した案

- 弾痕を 1 発ずつ数えて位置を測る: 弾痕が重なって筋になり、分けられない。
- ADS の倍率（約 1.45）で割って「実際に回った角度」にする: 倍率は腰だめと ADS の画面の比べ方による推定（1.43〜1.50 のばらつき）で、
  アプリには ADS の拡大がないため、アプリの同じ FOV では録画より小さく見える。換算の式もアプリと別になる。
- 範囲の透視の補正を範囲全体の重みつき平均で求める: アプリの式から外れた係数になり、テストで式から計算し直せない。
- 解析のスクリプト（Python・numpy・ffmpeg）をリポジトリに入れる: 動画がないと動かず、開発の依存が増える。
